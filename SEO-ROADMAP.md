### New data source: parties247 admin analytics API

Starting this cycle, `/seo-update` also pulls from `parties247_backend`'s own analytics
(`GET /api/admin/analytics/detailed`, JWT-protected, and the public
`GET /api/analytics/summary`) to see actual on-site conversion behavior (party views,
purchase-link clicks, visits) alongside GSC ranking data and Clarity engagement data.
`/api/analytics/summary`'s `trafficSources` breakdown for the live 24h window showed
**62.2% organic_search, 31.9% direct, 5.9% chatgpt.com** — the first direct evidence of
AI-assistant referral traffic reaching the site, a concrete GEO-effort signal (see Phase 3).
The same window's `devices` breakdown showed 21.8% of traffic tagged `bot` — worth keeping an
eye on but not actionable by itself.

**Anomaly root-caused and fixed same day (2026-08-04):** the `visits` field in
`/api/admin/analytics/detailed` was 0 for every day from 2026-07-06 through 2026-08-01, then
jumped to 5/56/111 on 08-02/03/04. Not a tracking bug — `visitor_analytics_collection` has a
MongoDB TTL index (`app.py`) that was deleting every document 172800 seconds (exactly 48h)
after `createdAt`. Confirmed via the raw `/api/admin/analytics/visitors?range=30d` endpoint:
all 171 records returned were dated within the last ~48h of the query, nothing older —
tracking was writing fine the whole time, MongoDB was just auto-deleting anything past 2 days
old. `build_time_series_analytics()` (backing the 7d/30d detailed endpoint) reads `visits`
from this same short-lived collection, so that column was structurally incapable of showing
anything beyond ~2 days regardless of real traffic. Fixed: extended the TTL to 35 days (covers
the 30d range with buffer) and fixed `ensure_index()` to also compare `expireAfterSeconds` —
previously it ignored that option when deciding whether to recreate an index, so this exact
kind of TTL change would have silently no-op'd on redeploy. Committed and pushed to
`parties247_backend` (`20eb582`); could not run the local test suite (pre-existing Flask/
flask_apscheduler version mismatch in the local Python env, unrelated to this change) or fully
confirm the Render redeploy picked it up (no version marker in the API to check from outside).
Real confirmation will only be visible in a few days once the collection has accumulated more
than 48h of un-purged data again.

## Revenue Findings (new, 2026-08-07)

- **Fixed 2026-08-17 — recurring weekly duplicate GoOut listings, not just one-off duplicates.**
  The 2026-08-07 dedup fix caught one-off same-event duplicates via exact `(name, date)`
  matching, but missed a *structural* case: recurring weekly events whose name embeds a
  differently-formatted date each listing (e.g. "THURSDAY MOON | MAINSTREAM | 06.08" vs
  "THURSDAY MOON | MAINSTREAM | 6.8 🏝️", plus an emoji difference) never matched exactly, so
  the same real Thursday event kept re-splitting into two GoOut listings nearly every week
  (confirmed via different `goOutEventId`s) — one earning (₪25.20–₪36.00/week, one of the
  site's best-converting account2 events per the 2026-08-12 conversion analysis) and one
  zero-revenue decoy siphoning 2–13 views/week away from it. Fixed `goout-scraper/
  dedupe_parties.py`'s matcher to group by brand-prefix + calendar day instead of exact string
  match (falls back to the old exact match when the prefix is too short/generic to be
  meaningful, avoiding false merges). Ran it: 25 duplicate parties deleted/redirected across 23
  groups (Thursday Moon Mainstream × 6 weeks, Saturday GOAT × 2, several one-off pairs).
  Deployed to the VPS; the daily automated dedupe pass will keep this series clean going
  forward instead of re-accumulating weekly.
- **Account1 (flat-fee, priority tier) is real, confirmed by the site owner as a genuine
  business gap, not a tracking bug.** Lifetime: account2 = ₪228.59 across 636 tracked
  party-rows vs account1 = ₪19.13 with 0 confirmed tickets across all 61 account1 rows.
  Real GoOut-side view/buyer counts (independent of our site) are also near-zero for
  account1 events, even for past events — so this isn't our funnel losing clicks, GoOut
  itself shows almost no engagement on these listings. BUT: when a party is dual-tracked
  by both accounts, the existing `_reconcile_dual_account_referrals` logic keeps the site's
  referral on account1, and those dual-tracked parties DO convert (4 purchases, ₪19.13, in
  the last 30d) — proof the account1 referral mechanism works when it gets traffic. Gap is
  exposure, not a broken funnel. Feeds into the deferred best-sellers-carousel idea below.
- **Duplicate GoOut listings were fragmenting revenue/SEO — found and fixed.** 7 groups of
  same-event-different-listing duplicates existed (different GoOut EventSerials for the
  same real party). Worst case: "Revival Summer Festival 13-14.8" was 3 separate listings
  across 2 site URLs, splitting a real ₪38.28-earning page's traffic. Fixed at the code
  level (not a one-off): `goout-scraper/dedupe_parties.py` now keeps whichever duplicate has
  real revenue (was: cheapest price, backwards), redirects the deleted slug to the survivor
  via a new `party_redirects` backend collection + `parties247-website`'s `proxy.ts`, and
  runs automatically every daily scrape (`orchestrator.py::run_dedupe_pass`) instead of
  needing someone to remember to run it. Applied this cycle: 6 exact-duplicate pairs merged
  automatically (all zero-revenue, low stakes) + the Revival Festival cross-name duplicate
  merged manually into the earning page (different names — "🐪" vs "🐪 13-14.8" — so the
  exact name+date matcher didn't auto-catch it; redirect confirmed live end-to-end).
- **Deferred idea, not built this cycle:** a revenue-weighted "best sellers"/"trending"
  carousel. Homepage carousels are backend-curated (`/carousels` endpoint) with no automatic
  revenue weighting anywhere — each carousel's internal order is just date-sorted
  (`HotEventsCarousel.tsx`). Given the account1-exposure finding above, an auto-populated
  carousel ranked by real sales velocity (account1-weighted per the priority order) could
  directly address both gaps. Needs scoping as a real task before building.
- **Fixed 2026-08-12 — fabricated social-proof numbers removed from event pages.**
  `src/components/UrgencyComponents.tsx`'s `PeopleWatching` (`{count} אנשים צופים באירוע זה
  כרגע`) and `RecentPurchaseToast` (`{name} רכש/ה כרטיס {time}`) both generated their numbers/
  names from `Math.random()` — flagged 2026-08-11, site owner confirmed to remove rather than
  wire in real data this cycle. `PeopleWatching` was live on every `/event/[slug]` page (removed
  the import + usage + the component itself); `RecentPurchaseToast` was already dead code (never
  imported anywhere) — deleted along with the fake `NAMES`/`TIMES` arrays. A real-data version
  (real `realBuyerCount`/`realSalesPerDate` per party) would need a new public backend endpoint —
  the existing `/api/admin/analytics/sales` is JWT-gated as business-sensitive — deferred as a
  separate scoped task, not done this cycle. `npx tsc --noEmit` clean after the change.
- **Investigated 2026-08-12 — is the displayed ticket price ever false/stale? No.** Confirmed
  by reading the code: `party.ticketPrice` (what's shown on-site) is populated and refreshed by
  `parties247_backend/app.py`'s `scheduled_price_scan` cron (every 30 min), which re-fetches each
  upcoming party's live GoOut page and computes the true final price (`base × (1 +
  commission%)`), falling back to parsing GoOut's own FAQ schema text. This is a completely
  separate, working pipeline from the `ticket_price`/`event_revenue` fields documented as
  "always null" in `goout-scraper/CLAUDE.md` — that null-data bug is specific to the internal
  sales-tracker's revenue-calculation field, unrelated to what visitors see. The number shown is
  real and current, just explicitly a *minimum starting price* with an on-page disclaimer that
  GoOut's final checkout total may differ — not a bug, but a legitimate source of the
  redirect-without-purchase gap on higher-priced events (see Ritual Festival Eilat below).
- **Redirect→purchase gap analyzed 2026-08-12 — not a systemic leak, concentrated in 3 events.**
  Site-wide 30d: 261 redirects → 43 purchases (16.5%). Broken down by the 12 parties with ≥5
  redirects (126 of the 261 total): most convert fine to well (Argentina vs England 89%,
  Thursday Moon Mainstream 67%, Golden Hour/Club Hop 40%, Ultra Show 31%) — the 0% conversions
  are concentrated in 3 events: **Ritual Festival Eilat** (23 redirects, ₪322.9 ticket price vs.
  the site's ~₪100 norm, 0 buyers ever on GoOut's own lifetime numbers — real price/checkout
  friction on GoOut's side, not fixable in our page copy); **MAINSTREAM - FRIDAY 14.08** (11
  redirects, ₪101 normal price — this is the exact page the 2026-08-11 cycle fixed a
  price-disclaimer dead-click bug on; most of this 30d window predates that fix, too early to
  judge); **SUMMER FESTIVAL 12.8** (7 redirects, ₪100.7 normal price, event is same-day as this
  analysis — too early in its own sales cycle to read anything into). No further action taken —
  one is external/GoOut-side, one already has a fix in flight, one is premature data.
- **Account1 exposure gap — reconfirmed unchanged, scope clarified 2026-08-12.** Still 0 pure
  account1-only parties; all 38 account1-tagged parties in the 30d funnel are dual-tracked with
  account2. Site owner confirmed dual-tracking itself is expected/fine (common for the same
  GoOut event to be visible to both accounts) and that the only requirement is the *live buy
  link* always being account1's when dual — which `_reconcile_dual_account_referrals` in
  `goout-scraper/sales_tracker.py` already enforces every 4h (fixed 2026-08-07). The remaining
  gap is that account1 discovers zero events on its own — a `goout-scraper` discovery-logic
  question, out of `/seo-update`'s scope (not a website change).
